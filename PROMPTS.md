# AI Prompts

This project was built with AI-assisted coding: **Claude Code** (Claude Opus 5.5) in VS Code.

This file has three sections:

1. **Build prompts:** a structured, step-by-step prompt sequence for the project. I wrote it after the build to document the design decisions. Each prompt covers one part of the system and can be run in order to rebuild the project.
2. **Runtime prompts:** the prompts the app itself sends to Llama 3.3.
3. **Session log:** the prompts I actually typed during development, word for word.

## 1. Build prompts

### Step 1: Architecture and plan

> I'm building an AI-powered app on Cloudflare for an assignment. It must include an LLM, workflow/coordination, chat input, and memory/state.
>
> Design a chat assistant called **"Recall"** that remembers the user across a conversation. Use:
> - **Workers AI** with `@cf/meta/llama-3.3-70b-instruct-fp8-fast` for chat, with streamed responses
> - **One Durable Object per chat session**, storing the transcript and memory in its built-in SQLite storage
> - **A Cloudflare Workflow** that runs in the background to distill the conversation into long-term memory (a short summary plus a list of durable facts about the user). The next turns' system prompt includes that memory.
> - **A Worker** for the JSON/SSE API, with the chat UI served as Workers static assets
>
> Before writing code, give me the architecture, the request flow for one chat turn, the API surface, and the file layout. Keep short-term context (the last N messages) separate from long-term memory (summary and facts), so prompt size stays bounded.

**Result:** the architecture diagram and API table in the README. Short-term context is the last 20 messages. The memory workflow runs every 6 messages.

### Step 2: Project scaffold

> Scaffold the project in TypeScript with Wrangler 4. Package name: `cf_ai_memory_chat`.
>
> In `wrangler.jsonc`, configure:
> - `main: src/index.ts`, a recent `compatibility_date`, and `nodejs_compat`
> - static assets from `./public`
> - an `AI` binding
> - a Durable Object binding `CHAT_SESSION` → class `ChatSession`, with a `new_sqlite_classes` migration
> - a Workflow binding `MEMORY_WORKFLOW` → class `MemoryWorkflow`
> - observability enabled
>
> Add a strict `tsconfig.json` that uses the types generated by `wrangler types` instead of `@cloudflare/workers-types`. Add npm scripts for `dev`, `deploy`, `types`, and `typecheck`, and a `.gitignore`. Add short comments in `wrangler.jsonc` saying what each binding is for.

**Result:** `package.json`, `wrangler.jsonc`, `tsconfig.json`, `.gitignore`, `worker-configuration.d.ts`.

### Step 3: Shared LLM helpers

> Create `src/llm.ts` with:
> - a `MODEL` constant for Llama 3.3 70B fp8-fast
> - `ChatMessage` (`role`, `content`, `createdAt`) and `Memory` (`summary`, `facts[]`, `updatedAt`) types
> - `buildSystemPrompt(memory)`: a concise persona for "Recall" that tells the model to use memory naturally and never invent facts. Add the summary and a bulleted fact list only when they are non-empty.
> - `parseSseToken(line)`: extracts the `response` token from one Workers AI SSE line (`data: {...}`). It returns `""` for `[DONE]`, blank lines, and malformed JSON, and never throws.

**Result:** `src/llm.ts`.

### Step 4: `ChatSession` Durable Object

> Implement `ChatSession` in `src/chat-session.ts`, extending `DurableObject<Env>`, with its API exposed as RPC methods.
>
> **Storage (SQLite, created in the constructor):**
> - a `messages` table (autoincrement id, role, content, created_at)
> - a single-row `memory` table (summary, facts as JSON, updated_at, workflow_id)
>
> **`chat(sessionId, userMessage)`** returns a `ReadableStream`:
> 1. Save the user message.
> 2. Build the prompt: the system prompt from memory, plus the last 20 messages.
> 3. Call Workers AI with `stream: true` and `max_tokens: 1024`.
> 4. `tee()` the stream. Return one branch to the caller. Read the other branch inside `ctx.waitUntil`, rebuild the full reply with `parseSseToken`, and save it as the assistant message.
> 5. After saving, if the total message count is a multiple of 6, start the memory workflow.
>
> Also add `getMessages(limit)` (oldest first), `getMemory()`, `saveMemory(summary, facts)`, `getWorkflowId()`, `refreshMemory(sessionId)` (starts a workflow run and records its id), and `reset()`.

**Result:** `src/chat-session.ts`.

### Step 5: `MemoryWorkflow`

> Implement `MemoryWorkflow` in `src/memory-workflow.ts`, extending `WorkflowEntrypoint<Env, { sessionId }>`. Use three `step.do` steps, so each is checkpointed and retried on its own:
>
> 1. **load conversation:** use RPC to fetch the current memory and the last 40 messages from the session's Durable Object. Return a plain, serializable snapshot.
> 2. **distill memory with llm:** call Llama 3.3 with a system prompt that merges the existing memory with the new transcript into `{ summary, facts }`. The summary is 2–4 sentences. Facts are durable facts about the user only, at most 12, and contradicted facts are dropped. Use `response_format` with a JSON schema. Retry 3 times with a 5-second exponential backoff and a 2-minute timeout.
> 3. **save memory:** write the result back through `saveMemory`.
>
> Validate the model output defensively. Accept an object or a JSON string, check its shape, drop empty or non-string facts, and cap facts at 12.

**Result:** `src/memory-workflow.ts`.

### Step 6: Worker API

> Write the Worker entry in `src/index.ts`. Re-export `ChatSession` and `MemoryWorkflow`, and route these endpoints:
>
> - `POST /api/chat {sessionId, message}` → stream the Durable Object's reply as `text/event-stream`
> - `GET /api/session?sessionId=` → `{ messages, memory, workflow }`, where `workflow` is the latest workflow run's id and status from `MEMORY_WORKFLOW.get(id).status()`
> - `POST /api/memory/refresh {sessionId}` → start the workflow now, return `202 { workflowId }`
> - `POST /api/reset {sessionId}` → clear the session
>
> Map `sessionId` to a Durable Object with `idFromName`. Validate at the edge: session ids must match `^[A-Za-z0-9-]{8,64}$`, messages must be 1–4000 characters, and a malformed JSON body should return a 400, not an exception. Unknown `/api/*` paths return a JSON 404. Use `satisfies ExportedHandler<Env>`.

**Result:** `src/index.ts`.

### Step 7: Chat UI

> Build the frontend in `public/` with plain HTML, CSS, and JavaScript, and no build step:
>
> - **Layout:** a chat column (header with a "New chat" button, message list, auto-growing textarea) and a **Memory** sidebar showing the summary, the facts, a "last updated" time, a workflow-status badge, and an "Update memory now" button.
> - **Session:** a `crypto.randomUUID()` session id kept in `localStorage`. Load the transcript and memory on page load.
> - **Streaming:** POST to `/api/chat`, read the body with a `TextDecoderStream`, parse the SSE lines, and add tokens to the assistant bubble as they arrive, with a blinking cursor while it's pending. Show API errors inline.
> - **Memory panel:** after each reply, refresh the session. While the workflow is `queued`, `running`, or `waiting`, poll every 2 seconds so the panel updates live.
> - Enter sends and Shift+Enter adds a newline. Render all model output with `textContent`, never `innerHTML`.
> - **Styling:** clean and minimal with a Cloudflare-orange accent, automatic dark mode, and a stacked layout below 800px.

**Result:** `public/index.html`, `public/app.js`, `public/styles.css`.

### Step 8: Verify and harden

> Run `wrangler types` and `tsc --noEmit`, then smoke-test every endpoint under `wrangler dev`: static assets, input validation, message persistence across requests, reset, and starting a workflow and reading its status.
>
> Fix anything that behaves badly. In particular, a failed Workers AI call must not send a stack trace to the client. Log it and return a `502` with a friendly JSON error that the UI can display.

**Result:** all checks passed. Found and fixed an unhandled model-failure path in `/api/chat`, which now returns a clean 502.

## 2. Runtime prompts (sent to Llama 3.3 by the app)

### Chat system prompt (`src/llm.ts` → `buildSystemPrompt`)

```
You are Recall, a friendly and concise assistant running on Cloudflare Workers AI.
You have long-term memory about the user that persists across the conversation.
Use it naturally when relevant, but never invent facts that are not in memory or the chat.
Answer in Markdown-free plain text unless the user asks for code.

Summary of the conversation so far:
<summary from memory>

Known facts about the user:
- <fact 1>
- <fact 2>
```

### Memory extraction prompt (`src/memory-workflow.ts` → `EXTRACTION_PROMPT`)

This prompt is sent with a JSON-schema `response_format` (`{ summary: string, facts: string[] }`):

```
You maintain long-term memory for a chat assistant.
Given the existing memory and the latest conversation, return JSON with:
- "summary": 2-4 sentences describing what the conversation has been about.
- "facts": up to 12 short, durable facts about the user (name, preferences, goals, projects, constraints).
Merge with existing facts, drop ones that were contradicted, and never include facts about the assistant.
Respond with JSON only.
```

The user message sent with it contains the existing summary, the existing facts, and the last 40 messages of the transcript.
